# Contractility

Локальный прототип для распознавания сканированных договоров и подготовки
дополнительных соглашений. PDF.js отрисовывает страницы в браузере,
Tesseract.js распознаёт русский и английский текст, а результат связывается с
отдельно выбранной новой редакцией допсоглашения DOCX через контрольные суммы.

## Запуск в закрытом контуре

На целевом компьютере `npm install` не выполняется. Репозиторий уже содержит
необходимые браузерные файлы, WebAssembly-ядро и языковые модели в
`public/vendor`.

Требования времени выполнения:

- Node.js 22 или новее;
- актуальный Chrome, Edge или Firefox с WebAssembly и Web Workers.

```bash
node scripts/doctor.mjs
node src/server.mjs
```

После запуска откройте `http://127.0.0.1:4317`.

Сервер использует только стандартную библиотеку Node.js, слушает loopback-адрес
и не предоставляет API загрузки документов. PDF выбирается непосредственно в
браузере и не отправляется во внешнюю сеть.

## Возможности текущего MVP

- открытие комплекта локальных PDF без загрузки на сервер: первый файл
  определяется как исходный подписанный договор, остальные — как подписанные
  дополнительные соглашения;
- изменение порядка подписанных допсоглашений без возможности переместить их
  перед исходным договором;
- добавление новых PDF в уже выбранный комплект без сброса обработанных страниц;
- отдельная загрузка предлагаемого дополнительного соглашения в DOCX: оно
  задаёт требуемые изменения и служит шаблоном итогового документа, но не
  попадает в цепочку ранее подписанных документов;
- использование готового текстового слоя, если он присутствует;
- OCR сканированных страниц на русском и английском языках;
- настройка 160, 220 или 300 DPI;
- автоматическое приведение альбомных сканов к книжной ориентации и ручной
  выбор поворота на 90°/180° для нестандартных документов;
- текст, уверенность OCR и координаты строк по каждой странице;
- ручное исправление распознанного текста;
- сохранение полностью распознанной сессии в переносимый
  `*.contractility.json` и её загрузка без повторного OCR;
- экспорт `*.formation-request.json` и `*.formation-request.txt` со строгим
  четырёхэтапным заданием на реконструкцию и формирование;
- SHA-256 каждого PDF, предлагаемого дополнительного соглашения DOCX и
  vendored-компонентов;
- полностью локальные модели без CDN.

## Диагностика на целевом компьютере

Если страницы завершаются с ошибкой внутри браузерного OCR, сначала выполните
обычные проверки, затем запустите диагностическую страницу:

```bash
npm test
node scripts/doctor.mjs
npm run diagnostics
```

В Safari откройте `http://127.0.0.1:4317/diagnostics.html`, выберите проблемный
PDF, дождитесь завершения и скачайте `*.diagnostics.json`. Проверка обрабатывает
только первую страницу на 220 DPI, повторяет точный вызов приложения, проверяет
структуру OCR-блоков и постобработку строк. При ошибке распознавания она также
проверяет передачу изображения через Data URL. Отчёт содержит версию Safari,
этапы и стеки ошибок, но не содержит изображение или распознанный текст.
Если Safari падает уже на `PDF.js getTextContent`, проверка завершается сразу:
основное приложение должно пропустить текстовый слой и перейти к обычному OCR.

## Обновление vendored-компонентов

Команды этого раздела выполняются только на контролируемой машине сборки с
доступом к npm, а не на целевом компьютере:

```bash
npm install --ignore-scripts
npm run vendor
npm test
```

`npm run vendor` копирует только требуемые runtime-файлы и создаёт
`public/vendor/manifest.json` с SHA-256 каждого файла. Версии зафиксированы в
`package.json` и `package-lock.json`. Сведения о лицензиях приведены в
`THIRD_PARTY_NOTICES.md`.

## Формат результата

### Сохранённая сессия OCR

После завершения OCR кнопка «Сохранить сессию» создаёт один файл
`*.contractility.json` со схемой `contractility.workspace-snapshot.v1`. В него
входят распознанные страницы со всеми ручными правками и настройками, исходные
PDF и, если он был выбран, предлагаемый DOCX. Кнопка «Загрузить сохранённую
сессию» восстанавливает комплект, превью и готовность к формированию без нового
распознавания.

При загрузке приложение проверяет структуру снимка, размеры файлов, их связь с
OCR-метаданными и фактические SHA-256 всех вложений. Повреждённый снимок не
заменяет уже открытый комплект. Файл сессии содержит полный текст договоров и
оригиналы документов, поэтому его следует хранить как конфиденциальный. Из-за
base64-кодирования он примерно на треть больше суммы вложенных файлов.

### Пакет формирования

Внутренний OCR-результат использует схему `contractility.ocr.v2`. Итоговый
экспорт использует схему `contractility.formation-request.v1` и содержит:

- упорядоченный массив подписанных документов с ролями `contract` и
  `additional-agreement`;
- метаданные и SHA-256 отдельно передаваемого предлагаемого дополнительного
  соглашения DOCX;
- четыре обязательных операции: реконструкция исходной редакции,
  последовательное применение подписанных изменений, извлечение всех
  требуемых изменений из предлагаемого DOCX и генерация финального
  допсоглашения на его основе;
- правила разрешения коллизий, сохранения макета предлагаемого DOCX, привязки
  каждого изменения к источнику и обязательного ручного подтверждения.

Формат, нумерация и система приложений договора и ранее подписанных
допсоглашений могут отличаться от предлагаемого DOCX. Такое структурное
несовпадение само по себе не является конфликтом: проверяется полнота
смысловых изменений, а результат сохраняет макет предлагаемого DOCX.

Один PDF может содержать несколько самостоятельных соглашений. Producer
сопоставляет номер и дату указанного в каждом соглашении базового договора с
исходным договором, применяет только совпавшие соглашения и фиксирует все
включения и исключения с номерами страниц в
`artifacts/reconstruction-scope.json`. Полное изложение пункта в новой редакции
заменяет всё прежнее содержание этого пункта, включая не повторённые тарифные
ступени и исключения; отдельно нумерованные подпункты сохраняются, пока они
прямо не исключены или не заменены.

Для каждой распознанной страницы дополнительно хранятся:

- источник текста (`pdf-text` или `tesseract`);
- текст и уверенность;
- время обработки;
- поворот страницы;
- размеры изображения, переданного OCR;
- нормализованные координаты распознанных строк;
- признак ручного исправления.

В пакет формирования DOCX не встраивается: он передаётся семантическому модулю
отдельным файлом, а совпадение проверяется по SHA-256. Исключение — переносимый
файл сохранённой сессии, который содержит оригинальный DOCX целиком. Это
позволяет сохранить таблицы, сноски, поля, стили и связи исходного OOXML-пакета.

Target CLI исполняет `contractility.formation-request.v1`, сохраняет реестр
применённых изменений, проводит циклическое межмодельное ревью и выпускает
финальный DOCX только после ручного подтверждения проверенного хеша.

## Запуск семантического контура на целевой машине

Локальный сервер объединяет браузерный OCR и target-контур, рассчитанный на
Node.js 22+, GigaCode CLI и `zip`/`unzip`. На целевой
машине не выполняется `npm install`: все runtime-файлы приложения уже находятся
в репозитории.

1. Скопируйте конфигурацию и укажите реальные идентификаторы доступных моделей:

```bash
cp config/target.example.json config/target.json
```

Producer, арбитр и все reviewer-роли могут использовать один и тот же
идентификатор модели. При желании каждой роли можно назначить отдельную модель.
Чтобы использовать модель, выбранную в настройках самого GigaCode CLI, укажите
строку `"default"` во всех нужных полях. В этом режиме Contractility не передаёт
флаг `--model`, но проверяет, что CLI сообщил фактически выбранную модель:

```json
{
  "models": {
    "producer": "default",
    "synthesizer": "default",
    "reviewers": [
      { "id": "contract-reconstruction", "model": "default", "focus": "reconstruction" },
      { "id": "legal-delta", "model": "default", "focus": "legal delta" },
      { "id": "document-fidelity", "model": "default", "focus": "document fidelity" }
    ]
  }
}
```

Если указан явный идентификатор, но GigaCode API отвечает `404 Model not found`,
Contractility один раз автоматически повторяет тот же запрос с моделью
`"default"`. Такой failover отражается в событиях и диагностическом пакете.

Проверить CLI, зависимости и все уникальные модели:

```bash
npm run doctor:target -- --config config/target.json --smoke
```

2. Запустите локальный сервер:

```bash
npm start
```

Откройте `http://127.0.0.1:4317`. После загрузки документов и завершения OCR
кнопка «Запустить формирование»:

- локально передаёт PDF, DOCX и formation request на loopback-сервер;
- повторно проверяет SHA-256 и создаёт неизменяемый case bundle;
- запускает producer тремя наблюдаемыми стадиями: реконструкция договора,
  планирование изменений и применение плана к DOCX;
- создаёт внутри каждого раунда локальный `evidence/` с OCR-текстом по
  документам и страницам и запускает агентов из каталога этого раунда;
- каждую секунду показывает последнюю активность GigaCode: этап, модель,
  сессию, время и результат ответа без публикации его содержимого в API;
- сохраняет и отображает каждый независимый reviewer-отчёт сразу после его
  готовности, не ожидая остальных рецензентов;
- позволяет скачать кандидат DOCX;
- принимает ФИО проверяющего и подтверждает точные хеши;
- финализирует и отдаёт готовый DOCX.

Роли по умолчанию: реконструкция договора, юридическая дельта, внутренние
ссылки и реквизиты, целостность DOCX, доказательность и безопасность.

Если модель не может доказательно установить значение поля, реквизита или
фрагмента пункта, формирование не останавливается и значение не угадывается.
Оно остаётся незаполненным, в DOCX появляется маркер
`[ТРЕБУЕТСЯ ЗАПОЛНЕНИЕ ЧЕЛОВЕКОМ]`, а причина фиксируется в
`change-register.json.unresolvedFields`. Дополнительные соглашения с
неподтверждённой идентичностью помечаются `unresolved` и не применяются до
проверки человеком.

Управляющий API принимает запросы только для `127.0.0.1`/`localhost`, требует
одноразовый токен текущего процесса и проверяет `Origin`. Исходные файлы
передаются по одному потоком с ограничением размера и повторной проверкой
SHA-256. Временная staging-копия удаляется после создания case.

## Отладочные логи GigaCode

Для каждой попытки GigaCode автоматически создаётся безопасный сокращённый
отчёт `data/runs/RUN_ID/diagnostics/gigacode/*.diagnostic.json`. Он содержит
классификацию завершения, код процесса, таймауты, хеши потоков, счётчики типов
NDJSON-событий и ограниченные фрагменты финального ответа и stderr. Исходные
документы, prompt и аргументы инструментов в него не копируются.

В карточке запуска кнопка «Скачать диагностику» собирает один файл
`RUN_ID-diagnostics.json` со state, журналом событий, состояниями агентов,
сокращёнными отчётами всех попыток и безопасной частью конфигурации. Этот файл
может содержать финальные ответы модели и служебные сообщения, поэтому его
следует передавать только доверенному получателю.

Сырой поток GigaCode может содержать текст договора, поэтому по умолчанию он не
сохраняется. Для временной диагностики включите в `config/target.json`:

```json
{
  "storage": {
    "runRoot": "../data/runs",
    "retainAgentTranscripts": true
  }
}
```

Перезапустите `npm start` и создайте новый run. Для каждой роли и каждой попытки
в `data/runs/RUN_ID/transcripts/` будут создаваться:

- `*.stdout.ndjson` — сырой поток `stream-json`, доступный во время выполнения;
- `*.stderr.log` — диагностический stderr;
- `*.summary.json` — модель, роль, длительность, код завершения и таймауты.

```bash
tail -f data/runs/RUN_ID/transcripts/producer-reconstruct.attempt-1.stdout.ndjson
tail -f data/runs/RUN_ID/transcripts/producer-plan.attempt-1.stdout.ndjson
tail -f data/runs/RUN_ID/transcripts/producer-apply.attempt-1.stdout.ndjson
```

Каждый поток ограничен 2 МБ, каталог имеет права `0700`, файлы — `0600`.
Live-состояние каждой сессии хранится отдельно в `agent-status/`, а
`events.ndjson` содержит только значимые аудиторские события и не растёт на
каждом фрагменте stdout/stderr.
После диагностики верните `retainAgentTranscripts` в `false`. Уже запущенный
процесс нельзя начать логировать задним числом.

## Резервный запуск через CLI

UI является основным операторским сценарием. CLI можно использовать для
диагностики, автоматизации или восстановления:

```bash
npm run target -- prepare --request REQUEST.json --draft DRAFT.docx \
  --source document-1=CONTRACT.pdf --out data/cases
npm run target -- run --case data/cases/CASE_ID --config config/target.json
npm run target -- status --run data/runs/RUN_ID
npm run target -- approve \
  --run data/runs/RUN_ID \
  --candidate-sha256 HASH_ИЗ_STATE \
  --findings-sha256 HASH_ИЗ_STATE \
  --approver "ФИО проверяющего"

npm run target -- finalize --run data/runs/RUN_ID
npm run target -- verify --run data/runs/RUN_ID
```

`approval.json` является аудиторским подтверждением процесса, а не электронной
подписью. Финализация без него или после изменения кандидата невозможна.

## Параллельное ревью

Контур использует проверенный подход
[`RomanovAV/gigalphex`](https://github.com/RomanovAV/gigalphex):
параллельные read-only рецензенты, строгий формат замечаний, недоверенная
граница для reviewer output, единый арбитр и повторные review-раунды. В
Contractility этот подход расширен индивидуальной моделью для каждого
рецензента, юридическими ссылками на документ/страницу/пункт, проверкой хешей
входов после каждого агентного этапа и остановкой при отсутствии прогресса.

Полная последовательность команд для приёмочного прогона приведена в
[`TARGET_MACHINE_FULL_TEST.md`](TARGET_MACHINE_FULL_TEST.md). Инструкция
начинается с клонирования `RomanovAV/contractility` из Git и может
использоваться как операторский runbook на целевой машине.

Семантическая стадия может обращаться к настроенному внутреннему сервису
моделей GigaCode. Поэтому формулировка «без отправки файлов в сеть» относится
только к браузерному OCR; допустимость передачи текста договоров в модельный
контур должна быть подтверждена политикой целевой организации.
